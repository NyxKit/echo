# Library import engine

Implementation decision, 2026-10-07. This implements the intake and reconciliation requirements in the conversation-library spec. All examples and validation use generated records.

## Intake and limits

Use yauzl 3.4, a maintained central-directory ZIP reader with lazy entry streams and ZIP64 support. Permit stored and deflated entries only. Check CRC32 independently while copying, as well as declared and actual sizes. Reject encryption, split volumes, nonregular entries, traversal, duplicate paths, case/Unicode aliases, Windows devices, and file/directory collisions. The parser never chooses a physical destination: staging uses generated identifiers. [Parser API and limitations](https://github.com/thejoshwolfe/yauzl).

ZIP and folder transfer feed the same logical path manifest. Only files selected by the browser can enter it. One import may run at a time. Upload chunks are at most 1 MiB; compressed input is limited to 8 GiB, expanded input to 32 GiB, individual entries to 256 MiB, entries to 100,000, paths to 1,024 characters and 32 segments, and extraction to 30 minutes. Keep 256 MiB of free disk space available. JSON source parts are limited to 8 MiB and a conversation batch to 32 MiB/100,000 records. Candidate discovery is capped at 10,000 conversations; ambiguity review is capped at 1,000 records, 1,000 candidates per record, and 10,000 total candidate edges, and 8 MiB of serialized review evidence across the job. Accumulated participant membership is bounded to 1,000 labels/32 KiB. These are explicit bounds, with the synthetic calibration below; workloads near every independent limit simultaneously still need target-hardware checks. Limits return safe categories; private names and records appear only in the authenticated UI.

An incomplete transfer is not an accepted import. Acceptance freezes the manifest and starts a worker; disconnecting its browser does not cancel accepted work. Cancellation interrupts extraction and is checked during validation and before the atomic commit. Restart marks incomplete jobs interrupted and cleans their staged input with retry bookkeeping. Finished import summaries persist without retaining the original ZIP. A cleanup failure remains visible and retryable.

History checking and commit each have a 30-minute processing budget, with cancellation/deadline checks between groups and within record batches. Cancellation remains effective between preview and commit. The worker reports live conversation counts and message/candidate counters; the UI clears stale percentages between phases. Progress counters remain in memory, while phase boundaries and terminal results are persisted, avoiding filesystem synchronization on every progress event.

## Ownership and matching

Refinement, 2026-10-09: infer self from a unique common participant across at least two distinct, nonempty participant sets. For later imports, compare incoming sets with stored sets, requiring the inferred label to agree with the existing owner. A subset with ambiguous participants can instead inherit the existing owner when automatic conversation matching establishes overlapping message history. Explicit conflicting owner evidence continues to require review (conflicting stable IDs remain rejected). Exact titles and equal participant sets can corroborate a short thread with at least one ordered exact message anchor, or an identical nonempty message sequence; names alone cannot merge disjoint history. Candidates sharing only resolved self, without an equal title, are excluded. Multiple plausible matches and changed group membership remain subject to review. These rules are exercised only with generated fixtures.

An owner is an opaque persistent UUID, independent of display names and ChatGPT identity. Read explicit self metadata and participant self markers, otherwise apply the common-participant/history inference above and offer unresolved candidates for local review. Persist the resolution method alongside owner evidence. Only explicitly supported stable account identifiers (`owner.id` or `account_owner.id`, decimal string) establish a provider-scoped stable identity. Preserve exact evidence. A known stable ID or previously reviewed identical owner evidence can resolve routine imports; conflicting stable IDs are rejected. A label alone never authorizes joining an existing library. A correction changes the label/evidence mapping without replacing the UUID.

Matching algorithm `ordered-observations-v2` uses complete source observations and ordered one-to-one anchors. A full, previously resolved observation repeats without change. Otherwise, unique exact message records supply ordered anchors; automatic overlap requires at least three distinct anchors in the same relative order and consistent conversation evidence, or the exact-title/participant corroboration described above for short histories. Repeated identical records use their position between unambiguous anchors, never set membership. Unmatched older or newer records remain distinct. Changed observations bounded by matching neighboring anchors may become versions of an existing message only when sender, timestamp and surrounding evidence agree; conflicting fields remain visible alternatives. No import order is treated as authoritative recency.

Conversation titles, participant labels, source directories, message hashes and timestamps are candidate evidence, never sufficient alone. Ambiguous conversation or message identity is retained for review. Review offers explicit match or keep-separate decisions and stores the observation-to-identity mapping for subsequent imports. Unknown fields and exact numeric representations remain in immutable source/version records. Absence never deletes history.

Candidate discovery retains alternatives sharing a non-self participant or an exact title for review. Automatic anchor discovery reads message history only for equal participant sets, as required by the existing confidence rule. Explicit choices bypass anchor discovery; identical saved observations use their occurrence mappings directly. A single candidate history can be reused within a group, avoiding duplicate reads without retaining the whole library in memory.

## Transaction boundary

Validate each bounded source part and install managed bytes before committing references. Apply accepted conversations, occurrences, versions, review decisions and import provenance in one SQLite transaction. The worker processes bounded conversation groups and observes a shared cancellation flag. Failed or canceled work rolls back; installed but unreferenced bytes are reclaimable. Stable message IDs preserve reading positions and discussion anchors across ordinal changes.

## Delivery tracking

The 2026-10-09 history-checking regression uses `scripts/check-import-reconciliation.mjs`: 40 generated conversations sharing self, 500 existing messages each, and one added message per conversation. Preview time on this development host fell from 17.291 seconds to 0.494 seconds. The check verifies 40 additions, 20,000 matches and no duplicate history. A separate regression counts history reads while preserving all review candidates. These figures describe synthetic workloads only.

Intake, durable jobs, owner review, conservative reconciliation, the server-backed viewer, immutable analysis contexts, discussion persistence, deletion, tray/login adapters and packaging are implemented. Synthetic tests cover ZIP/folder equivalence, repeated imports, overlapping and older history, changed observations, missing and changed attachment bytes, owner correction/rejection, review persistence, cancellation and restart cleanup. A generated 32 MiB compressed entry exercises streaming extraction. `scripts/check-import-capacity.mjs` imports 100,000 generated records across four parts, repeats the import without additions, checks pagination and reopens the library: 13.95 seconds for the initial import and 29.39 seconds total, with 578 MiB peak process RSS on this Linux development host. The worker has a 256 MiB old-generation/32 MiB young-generation JS heap budget; native SQLite buffers are additional. A bounded prepared-statement cache and indexed source-occurrence lookups prevent repeated native allocations and large repeat-import scans. This measures one generated workload, not a guarantee for every maximum-size archive. Platform installation and live-provider checks are reported separately.
